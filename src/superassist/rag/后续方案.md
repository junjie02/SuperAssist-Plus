 > 当前代码里的 Agentic RAG 全流程是一个 LangGraph 状态机，不是“把检索封装成一个工具后直接相信结果”。
 >
 >   用户问题
 >     ↓
 >   Router 路由
 >     ↓
 >   Plan 任务拆解
 >     ↓
 >   Retrieve 检索
 >     ├─ 有结果 → 下一个子问题 / 生成答案
 >     ├─ 无结果 → Query Rewrite
 >     ├─ 连续无新增 → Backtrack 换检索路径
 >     ├─ 本地检索仍失败 → Web Fallback
 >     └─ 最终无结果 → Abstain 拒答
 >     ↓
 >   Synthesize 生成答案
 >     ↓
 >   Finalize
 >     ↓
 >   最终答案 + 来源 + RAG Trace
 >
 >   1. 进入 Agentic RAG
 >
 >   只有以下条件同时满足时才会走 Agentic Graph：
 >
 >   - 当前请求开启 rag_mode
 >   - 有 HybridRAGService
 >   - SUPERASSIST_AGENTIC_RAG_ENABLED=true
 >
 >   入口在 /F:/CODE/SuperAssist/superAssist/SuperAssist/src/superassist/agent/runtime.py:80。
 >
 >   否则会走旧的 RAG Middleware 路径。
 >
 >   2. Router 路由
 >
 >   当前 Router 是确定性规则，不是 LLM Router Agent：
 >
 >   - direct：用户明确要求不要检索
 >   - sql：出现数据库、订单、销售额、统计等关键词，且配置了 SQL Retriever
 >   - web：出现“最新、今天、实时、新闻”等关键词
 >   - uploaded_kb：默认走本地知识库
 >
 >   当前本地实际默认是：
 >
 >   HybridRAGService
 >       ├─ FAISS Dense
 >       ├─ SQLite FTS5 BM25
 >       └─ RRF 融合
 >
 >   SQL Retriever 目前只是接口预留，Runtime 没有默认注入，所以 SQL 路由目前不会真正访问关系型数据库。
 >
 >   3. Plan 规划
 >
 >   当前会把复杂问题按：
 >
 >   然后、并且、以及、同时、并、且、问号
 >
 >   拆成最多 4 个子问题，然后逐个检索。
 >
 >   这已经具备 Plan-and-Solve 的状态节点，但还不是 LLM 驱动的递归子问题规划器。当前规划器是规则拆分。
 >
 >   4. Retrieve 检索
 >
 >   本地知识库通过 /F:/CODE/SuperAssist/superAssist/SuperAssist/src/superassist/rag/agentic_contracts.py:96 接入 Agentic
 >   Graph。
 >
 >   每个结果会转换成稳定的：
 >
 >   evidence_id
 >
 >   并记录：
 >
 >   - 文档
 >   - Chunk
 >   - 来源
 >   - Dense rank
 >   - BM25 rank
 >   - RRF score
 >   - 可选 reranker score
 >
 >   当前生产默认不启用 Cross-Encoder：
 >
 >   SUPERASSIST_RAG_RERANKER_ENABLED=false
 >
 >   5. 检索结果分支
 >
 >   当前不再对检索结果做 relevance/coverage 证据校验。有结果时进入生成；无结果或连续没有新增结果时，进入重写、回退或 Web 兜底。
 >
 >   6. Query Rewrite
 >
 >   最多重写 3 次，目前有三种策略：
 >
 >   - keyword_extract：抽取关键词
 >   - aspect_expand：增加“定义、原因、影响、方法”
 >   - constraint_expand：增加“规定、流程、条件”
 >
 >   每次重写后会重新检索，并记录：
 >
 >   query_attempts
 >   retrieval_runs
 >   rewrite_count
 >
 >   7. Backtrack 状态回退
 >
 >   如果连续检索没有新增证据，会换检索模式：
 >
 >   dense → bm25 → hybrid → dense
 >
 >   最多回退 2 次。
 >
 >   这部分才是真正的状态机回退，不是简单地再次调用同一个检索工具。
 >
 >   8. Web Fallback
 >
 >   本地证据不足时，如果允许网络，会调用 web_search，把网页标题、摘要、URL 转成新的 Web Evidence，合并到证据池。
 >
 >   不过当前 Web 兜底仍比较基础：
 >
 >   - 使用搜索摘要
 >   - 没有独立网页可信度评分
 >   - 没有网页内容二次抓取验证
 >   - 没有来源可信等级模型
 >
 >   9. Synthesize 生成
 >
 >   生成提示词要求：
 >
 >   只能根据证据回答
 >   每个事实性结论必须引用 [ev-...]
 >   证据不足时明确说明
 >
 >   如果模型没有生成合法引用，系统会退化为从证据中摘取前三条，避免产生完全无来源的答案。
 >
 >   10. 生成后处理
 >
 >   生成结果直接进入 Finalize。系统保留 evidence_id 的引用渲染，但不再执行 claim 拆分、引用存在性校验、groundedness 评分或自动 Repair。
 >
 >   当前配置预算
 >
 >   最大状态步数：20
 >   最大检索次数：6
 >   最大 Query 重写：3
 >   最大回退次数：2
 >   最大子问题数：4
 >   Web fallback：开启
 >   单轮最长时间：45 秒
 >
 >   当前已经真正实现的部分
 >
 >   - LangGraph 状态机
 >   - Router
 >   - 基础 Plan
 >   - Dense/BM25/Hybrid 检索
 >   - 检索结果去重
 >   - Query Rewrite
 >   - Backtrack 换路径
 >   - Web Fallback
 >   - 带引用生成
 >   - 完整 rag_trace 和 answer_provenance
 >
 >   目前仍属于半成品或预留的部分
 >
 >   - Router 不是 LLM 决策
 >   - Plan 不是递归式子问题规划
 >   - 不再提供检索结果充分性评分或答案事实核验
 >   - SQL Retriever 未默认接入
 >   - OpenSearch/PostgreSQL 还不是当前运行后端
 >   - LangGraph 目前使用内存 Checkpointer，不能跨进程恢复
 >   - Web 结果没有完整的可信度和内容验证链
 >
 >   因此，当前系统保留 Agentic RAG 的路由、规划、重写、回退和兜底控制流，但不包含证据评分与生成后验证链路。
