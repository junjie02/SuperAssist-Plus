  一、推荐技术架构

  MinIO/S3             PostgreSQL                 OpenSearch
  原始文件        文档/版本/Chunk/ACL/任务      BM25 + Dense Vector
     │                    │                         │
     └──解析切片───────────┴──异步索引──────────────┘
                                                    │
  用户问题 → Agent查询改写 → 混合召回 → RRF融合 → 过滤去重
          → 邻接Chunk扩展 → Token预算组装 → 带Chunk引用回答

  - PostgreSQL：文档元数据、版本、Chunk 原文、权限、任务和检索审计
  - OpenSearch：BM25、向量检索、元数据过滤
  - MinIO/S3：保存不可变原文件
  - Redis：索引任务队列、状态和短期缓存

  如果只想部署一个数据库，可以使用 PostgreSQL + pgvector + pg_search，但从中文 BM25、横向扩展和运维成熟度看，企业方案优
  先选择 OpenSearch。

  二、企业级解析与切片

  现有 documents.py 基本是把整份文件扁平化为文本，会丢失标题层级、页码和表格结构，需要替换为结构化解析。

  处理流程：

  1. 上传校验：MIME 检测、扩展名校验、SHA-256 去重、大小/页数限制、病毒扫描。
  2. 格式解析：PDF/DOCX/PPTX 使用 Docling；扫描 PDF 增加 PaddleOCR；HTML、Markdown、CSV、XLSX 使用专用解析器。
  3. 文本清洗：Unicode 规范化、重复页眉页脚删除、断行修复、空白压缩，但保留原文和页码。
  4. 结构恢复：保留 heading_path、页码、段落、列表、表格、代码块、幻灯片编号。
  5. 版本管理：相同逻辑文档的新文件生成新版本，旧版本不直接覆盖。

  采用父子切片：

  - Child Chunk：约 350～400 Token，最多不超过 480 Token，按句子边界切分，重叠 50～60 Token
  - Parent Chunk：约 1000～1500 Token，只用于上下文扩展，不直接参与向量检索
  - 标题路径拼入 Child，例如：文档名 > 第三章 > 3.2 训练方法
  - 表格按表头加若干数据行切分，每个 Chunk 重复表头
  - 不跨章节切片；过短段落在同一章节内合并

  当前使用的 bge-base-zh-v1.5 最大输入长度约 512 Token，原来的 1200 Token Chunk 在生成 Embedding 时可能被截断，改成 350
  ～400 Token 会更合理。

  三、数据库模型

  核心表建议包括：

  documents          文档逻辑身份、租户、ACL、当前版本
  document_versions  文件Hash、解析器版本、状态、存储地址
  document_blocks    页、标题、段落、表格等结构化块
  chunks             原文、parent_id、页码、标题路径、Token数、Hash
  ingestion_jobs     解析/切片/Embedding/索引任务状态
  retrieval_runs     查询、过滤条件、耗时、Token预算
  retrieval_hits     Chunk、Dense/BM25排名、RRF分数、是否进入上下文

  所有检索必须在服务端强制附带 tenant_id + ACL + active_version 过滤，不能依赖 Agent 自己传权限条件。

  四、混合检索流程

  一次检索建议这样执行：

  原始查询
   ├─ Dense Top-50：BGE语义向量
   └─ BM25 Top-50：标题、章节、正文、编号关键词
                ↓
         RRF融合，不比较异构原始分数
                ↓
       去重、权限过滤、文档版本过滤
                ↓
         选取融合结果 Top-20
                ↓
       按需扩展相邻Chunk或Parent
                ↓
     按5000 Token证据预算组装上下文

  RRF 可以使用：

  score = 0.55 / (60 + dense_rank) + 0.45 / (60 + bm25_rank)

  中文 BM25 使用 SmartCN 或 IK Analyzer，同时保留标准分词字段匹配英文术语、模型名、错误码和编号。

  暂时不加 Cross-Encoder reranker。过滤阶段只做确定性逻辑：

  - Chunk ID 和内容 Hash 去重
  - 同一章节连续命中时合并
  - 单份文档最多占一定比例，避免结果被一篇文档垄断
  - 删除低质量、空白、导航、免责声明等 Chunk
  - 最终上下文严格按真实 Token 计数，不再使用字符数近似
  - 每条证据保留 document_id/version/page/chunk_id

  五、Agentic RAG 逻辑

  取消现在 RAG 专用的“最多三次”规则，但不能真的无限循环。企业系统应改成质量和预算驱动的停止机制：

  - 主 Agent 首次自动执行原问题 Hybrid 检索
  - 证据不足时，自主进行关键词化、同义词、缩写展开或问题拆分
  - 每次检索结果加入本轮累计证据池，并跨查询去重
  - 连续两次没有新增有效 Chunk 时停止
  - 达到证据 Token、总延迟或 Agent 总工具预算时停止
  - 保留 Runtime 层面的通用死循环保护，但不设置 RAG 固定三次限制

  rag_search 工具建议改为：

  {
    "query": "改写后的查询",
    "search_type": "hybrid|dense|bm25",
    "filters": {"document_ids": [], "date_from": null},
    "top_k": 20,
    "evidence_token_budget": 5000
  }

  最终回答中的每个重要结论必须引用真实 Chunk，例如 [技术白皮书.pdf#page=12&chunk=c-103]，服务端再验证引用 ID 确实来自本
  轮检索。
