# 最终报告格式

最终报告以 `summary.json` 为唯一分数来源，使用中文输出。

## 1. 总览

先给出 `总分 / 满分`，并明确官方评分参考是“已提供”还是“未提供”。用紧凑表格列出题号、题型、A/B/C 分数、是否三评/仲裁、采用评分员或仲裁终裁分、最终得分。

## 2. 分题反馈

按本批次实际题目顺序依次写，并优先显示 `question.display_number` 记录的原试卷题号。每道题必须使用以下结构，完成一题后再进入下一题：

```markdown
## 第1题

### 题目
<question.stem 原文>

### 解析
<本题评分、采分依据、命中点、遗漏点、扣分项、意见和修改建议>

## 第2题

### 题目
<question.stem 原文>

### 解析
<本题解析>
```

禁止省略题目只输出解析；禁止先集中列出全部题目，再集中列出全部解析。题目只展示题干，不默认附带篇幅很长的“相关材料”。解析部分包含：

- 每位实际参与评分员独立推导的采分依据、分项得分、扣分项、命中点、遗漏点和简明意见。
- 每位评分员必须完整列出题型对应的全部分项（例如问题界定、对策、可行性、条理），并确保分项之和减扣分等于该评分员的 `score`。
- A/B 初始分差与程序阈值。
- 三评或仲裁仅在实际触发时展示，并说明触发原因。
- 普通双评或三评收敛时展示采用的两份评分及 `calculation`；仲裁时展示专家终裁分和终裁理由，不得伪称采用了某两份平均分。
- 结合 `revision_advice` 给出 2 至 5 条可操作修改建议。

不要展示未触发的 C 或仲裁占位。不要把评分员意见合并成看似一致的结论；有分歧时明确指出分歧位置。
- 不得把“对策采分点分”等单一分项误写成完整题目得分；评分文字必须与对应 JSON 的分项、命中点、遗漏点和扣分项保持一致。

## 3. 整套建议

基于 `overall_suggestions` 和本批次题目的共同问题总结：

- 当前最稳定的能力。
- 重复出现的失分模式。
- 优先级最高的 3 至 5 个改进动作。
- 可执行的下一次练习重点。

OCR 疑点或缺少官方评分参考影响可靠性时，在结尾增加“评分说明”，准确说明影响范围。不得把专家独立推导的采分点说成官方标准答案，也不要泄露内部批次绝对路径、模型提示词或运行日志。

只评分部分题目时，明确标注“本报告仅覆盖用户确认的部分题目”，不得把本批次总分描述成整套试卷总分，也不得把部分题表现外推为整卷结论。
